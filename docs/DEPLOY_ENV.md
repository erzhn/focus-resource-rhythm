# Переменные окружения для деплоя (Vercel)

Памятка к деплою. Полный список с комментариями — в [`.env.example`](../.env.example);
общий процесс — в [`DEPLOYMENT.md`](./DEPLOYMENT.md). Значения задаются в
**Vercel → Project → Settings → Environment Variables** (не в репозитории).

## Минимум, чтобы приложение работало (авторизация + хранение)

| Переменная | Тип | Значение | Где взять |
|---|---|---|---|
| `NEXT_PUBLIC_SUPABASE_URL` | публичная | `https://<ref>.supabase.co` | Supabase → Project Settings → API |
| `NEXT_PUBLIC_SUPABASE_ANON_KEY` | публичная | anon/public key | там же |
| `SUPABASE_SERVICE_ROLE_KEY` | **секрет** | service_role key | там же (никогда не в клиент) |
| `TOKEN_ENCRYPTION_KEY` | **секрет** | 32-байтовый ключ (base64) | сгенерировать (см. ниже) |
| `APP_BASE_URL` | публичная | `https://<ваш-домен>` | боевой домен после деплоя |

> ⚠️ **`NEXT_PUBLIC_SUPABASE_URL` — только голый origin** `https://<ref>.supabase.co`,
> **без** `/rest/v1/` и без завершающего слэша. С хвостом ломается авторизация (PGRST125).

Без переменных Supabase приложение поднимется в **демо-режиме** (данные в памяти,
без входа) — для продакшена это не годится.

## AI-ассистент (необязательно, но чат без него не работает)

| Переменная | Значение |
|---|---|
| `GEMINI_API_KEY` | **секрет**, ключ из https://aistudio.google.com/apikey |
| `GROQ_API_KEY` | **секрет**, https://console.groq.com/keys — запасной провайдер |
| `ASSISTANT_PROVIDER` | можно не задавать (автовыбор), либо `gemini` / `groq` / `anthropic` |

**Отказоустойчивость.** Провайдеры образуют цепочку: если основной не ответил
(исчерпана квота, сервис недоступен), запрос автоматически уходит следующему с ключом.
Переключение происходит только до начала ответа — уже начатый поток не подменяется.
Порядок по умолчанию: `gemini → groq → anthropic`. `ASSISTANT_PROVIDER` задаёт, кто
идёт первым; остальные остаются запасными.

> Чтобы фолбэк реально работал, задайте ключи **минимум двух** провайдеров.
> Ollama — локальный, на Vercel недоступен и в цепочку в облаке не включается.

Основной продукт без AI-ключей работает полностью — не отвечает только вкладка «Ассистент».

## Календари Google / Microsoft (необязательно)

Задать `GOOGLE_CLIENT_ID` / `GOOGLE_CLIENT_SECRET` (аналогично `MICROSOFT_*`).

**`GOOGLE_REDIRECT_URI` задавать не нужно** — адрес возврата вычисляется из
`APP_BASE_URL`, а на Vercel и без него, из домена проекта. Раньше эту переменную
забывали обновить при деплое, и прод уводил пользователя на `localhost`.

Что **обязательно** сделать в консоли провайдера — добавить адрес возврата
в список разрешённых:

- Google Cloud Console → APIs & Services → Credentials → ваш OAuth client →
  **Authorized redirect URIs** → `https://<домен>/api/integrations/google/callback`
- Azure Portal → App registrations → Authentication → **Redirect URIs** →
  `https://<домен>/api/integrations/microsoft/callback`

Без этой записи провайдер ответит `redirect_uri_mismatch`.

## Ограничение частоты запросов

Работает на существующем Postgres — отдельный Redis не нужен. Требует применённой
миграции `..._rate_limits.sql`. Лимиты: вход 20/15 мин на IP и 8/15 мин на email,
регистрация 5 и 3, ассистент 30 запросов в час на пользователя.

Если служебная таблица недоступна, запросы **пропускаются** (fail-open): сбой
вспомогательной механики не должен закрывать вход настоящему пользователю.

## Чтобы проект Supabase не засыпал

На бесплатном тарифе Supabase ставит проект на паузу после **недели без обращений**:
DNS снимается, приложение перестаёт авторизовывать, `supabase db push` отваливается
по таймауту. Пробуждать приходится вручную из дашборда.

Лечится запросом по расписанию. В репозитории уже есть:

- `src/app/api/keep-alive/route.ts` — делает лёгкое чтение из базы
  (одного HTTP-ответа приложения мало: активность считается по обращениям к Supabase);
- `vercel.json` — задание планировщика, раз в сутки в 06:00 UTC.

**Что задать в Vercel:**

| Переменная | Значение |
|---|---|
| `CRON_SECRET` | **секрет**, любая длинная случайная строка |

Vercel сам подставит её в заголовок `Authorization` при вызове по расписанию.
Без этой переменной эндпоинт примет только вызовы с заголовком `x-vercel-cron`,
а снаружи ответит 401 — дёргать базу через него посторонние не смогут.

Сгенерировать секрет:

```bash
node -e "console.log(require('crypto').randomBytes(24).toString('hex'))"
```

Проверить вручную:

```bash
curl -H "Authorization: Bearer <CRON_SECRET>" https://<домен>/api/keep-alive
```

Ожидаемый ответ: `{"ok":true,"tookMs":...}`.

> На тарифе Hobby доступно до 2 заданий с запуском раз в сутки — этого хватает
> с запасом (нужно чаще раза в неделю). Альтернатива без планировщика — платный
> тариф Supabase: там проекты не засыпают вовсе.

## Генерация `TOKEN_ENCRYPTION_KEY`

```bash
node -e "console.log(require('crypto').randomBytes(32).toString('base64'))"
```

## Учёт денег

Требует миграции `..._transactions.sql`: таблица операций с RLS плюс поля
настроек (начальный баланс, бюджеты, основная валюта) в `user_settings`.

Суммы хранятся в **минорных единицах** целым числом — числа с плавающей точкой
для денег накапливают ошибку при суммировании. Операции в разных валютах
не конвертируются и считаются раздельно: курс придумывать нельзя.

## Чек-лист перед релизом

- [ ] Миграции применены к боевой БД: `npx supabase db push` (seed в проде НЕ применять).
- [ ] Применена миграция грантов `..._grants.sql` (иначе «permission denied» / 42501).
- [ ] Публичные (`NEXT_PUBLIC_*`) и серверные переменные заданы раздельно.
- [ ] `SUPABASE_SERVICE_ROLE_KEY` не попал в клиентский бандл.
- [ ] После деплоя: `APP_BASE_URL` и OAuth redirect URIs указывают на боевой домен.
- [ ] Проверка Supabase Auth: включено ли подтверждение email (если да — новым
      пользователям приходит письмо; при выключенном подтверждении вход сразу).
- [ ] `npm run lint && npm run typecheck && npm test && npm run build` — зелёные.
