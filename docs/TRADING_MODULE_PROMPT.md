## 1. Роль и результат

Ты — senior full-stack инженер и продуктовый дизайнер. Добавляешь в существующий
сайт законченный модуль **«Торговля»**: журнал сделок, учёт торгового счёта,
Telegram-ввод, контроль торговых правил и аналитика.

Нужен личный инструмент с выразительным интерфейсом и надёжными расчётами. Все
основные действия должны работать: от проверки плана сделки до её закрытия,
разбора и появления в отчётах.

Критерии качества:

1. **Понятность:** за несколько секунд видно состояние счёта, открытые сделки и
   соблюдение правил.
2. **Удобство:** запись сделки — минимум действий; подробный разбор можно
   закончить позже.
3. **Достоверность:** расчёты воспроизводимы, неизвестные значения обозначены,
   история не меняется от редактирования настроек.
4. **Дизайн:** модуль выглядит как качественный финансовый продукт и неотличим
   по языку от остального сайта.

Описания архитектуры, статичного дашборда и демонстрационных кнопок
недостаточно. Нужен работающий модуль в репозитории.

### 2.3. Конвенции базы

34 таблицы, 11 миграций, соглашения выдержаны единообразно. Новые таблицы
делать так же:

```sql
create table if not exists public.trading_example (
  id         uuid primary key default gen_random_uuid(),
  user_id    uuid not null references auth.users(id) on delete cascade,
  -- ...
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);

comment on table public.trading_example is 'Одно предложение по-русски: что это и почему.';

create index if not exists idx_trading_example_user on public.trading_example (user_id, created_at desc);

create trigger trg_trading_example_updated before update on public.trading_example
  for each row execute function public.set_updated_at();

alter table public.trading_example enable row level security;

create policy trading_example_select_own on public.trading_example
  for select using (auth.uid() = user_id);
create policy trading_example_insert_own on public.trading_example
  for insert with check (auth.uid() = user_id);
create policy trading_example_update_own on public.trading_example
  for update using (auth.uid() = user_id) with check (auth.uid() = user_id);
create policy trading_example_delete_own on public.trading_example
  for delete using (auth.uid() = user_id);

grant select, insert, update, delete on public.trading_example to authenticated;
grant all on public.trading_example to service_role;
```

### 2.4. Деньги и время: два модуля живут по-разному

**Деньги.** Личные финансы хранят суммы как `bigint` в минорных единицах.
Торговля использует `numeric` — разные рынки, разные множители, дробные объёмы.
Это сознательное расхождение; финансы не переделывать.

**Время.** Финансовый день в личных финансах считается по **фиксированному
смещению UTC+6** (`src/domain/finance/day.ts`) — это задокументированное решение
для Кыргызстана без перехода на летнее время. Для торговли так нельзя:
у торгового счёта хранится IANA-зона, локальная дата считается через
`at time zone`. Финансовый модуль не менять.

### 2.6. Фоновая обработка: что есть и чего нет

`vercel.json` содержит ровно два cron, **оба раз в сутки**:
`/api/keep-alive` в 06:00 UTC и `/api/telegram/daily-report` в 16:00 UTC.
Очереди, воркера, inbox и outbox нет.

Тариф хостинга на момент аудита не подтверждён, а суточная частота
соответствует ограничениям бесплатного тарифа. Поэтому **механизм напоминаний
обязан не зависеть от частоты запуска**: эндпоинт идемпотентен по ключу
`(user_id, account_id, локальная дата, тип напоминания)` и безопасен при вызове
хоть раз в сутки, хоть каждый час. Тогда переход на более частое расписание —
одна строка в `vercel.json` или внешний планировщик, без правок кода.

### 2.7. Telegram: три реальных пробела

Бот учёта расходов работает (`src/app/api/telegram/webhook/route.ts`,
`src/app/api/telegram/daily-report/route.ts`, привязка —
`src/app/(app)/settings/telegram-actions.ts`). В нём три дефекта, которые этот
модуль обязан закрыть, потому что иначе торговые операции унаследуют те же
проблемы:

1. **`telegram_links.link_code` хранится открытым текстом.** Нужен хеш
   одноразового токена, срок жизни и атомарное погашение.
2. **Идемпотентности нет вообще:** `update_id` нигде не проверяется. Повторная
   доставка апдейта прямо сейчас создаёт вторую операцию расхода.
3. **Обработка синхронная внутри запроса**, без состояний, повторов и
   восстановления зависшей обработки.

Чинить их нужно так, чтобы существующий ввод расходов продолжал работать.

## 3. Решения, принятые по итогам аудита

Эти вопросы уже закрыты. Менять — только по прямому указанию владельца.

| № | Решение | Почему |
|---|---|---|
| 1 | **Математическое ядро — на TypeScript в `src/domain/trading/`**, исполняется только на сервере. SQL занимается исключительно агрегацией уже сохранённых значений | Docker недоступен, pgTAP не настроен, тестировать plpgsql нечем. 33 числовых теста обязаны идти в обычном `npm test`. Реализация формул остаётся ровно одна, как и требовалось |
| 2 | **Денежные поля отдаются из views/RPC как `::text`.** Фронтенд их только форматирует и никогда не считает | `supabase-js` десериализует `numeric` в JS `number` (float) — точность теряется до попадания в код |
| 3 | **Производные значения сохраняются снимком** при записи события, а не пересчитываются при чтении | Совпадает с требованием «история не меняется от редактирования настроек» |
| 4 | **Тот же Telegram-бот.** Торговые действия — только по явным командам (`/in`, `/log`, `/out`…). Свободный текст по-прежнему означает расход | Второй бот = второй токен, второй вебхук, вторая привязка |
| 5 | **Демо-сделки — флаг `trading_accounts.is_demo`** в настоящей базе | Существующий демо-режим приложения — это работа вообще без Supabase; это другое |
| 6 | **Один пункт навигации «Торговля»** с вкладками внутри. В нижнюю панель телефона не добавлять | Там уже 5 из 5 `primary` пунктов |
| 7 | **Связь владельца parent↔child — составными ключами:** `unique (id, user_id)` на родителе + составной внешний ключ с дочерней таблицы | Одного `user_id` в дочерней таблице недостаточно: он не доказывает, что сделка принадлежит счёту того же владельца |
| 8 | **Views создавать с `security_invoker = true`** | PostgreSQL 17.6 это поддерживает. `security definer` для обхода ошибок доступа не применять |
| 9 | **Напоминания идемпотентны по ключу** `(user, account, локальная дата, тип)` | Частота cron может меняться; повтор не должен рассылать одно и то же дважды |

## 4. Границы первой версии

**Входит:** личные торговые счета с одним владельцем; справочник рынков и
инструментов; линейная расчётная модель с конвертацией валют; один вход и
несколько выходов на сделку; русский интерфейс; зона `Asia/Bishkek` по
умолчанию, настраиваемая; ручной ввод сделок и экономических событий;
аналитика без платного ИИ и без платного источника котировок.

**Не входит:** исполнение ордеров у брокера, торговые сигналы, автоматическая
торговля, усреднение позиции, копитрейдинг, подписки, публичные рейтинги,
импорт брокерских отчётов. Опционы, инверсные крипто-контракты и другие
нелинейные модели по формуле линейного инструмента **не рассчитывать**.

Депозит ориентировочно $40–100. XAU/USD — один из инструментов, а не
ограничение продукта. В базе, формулах, seed и интерфейсе не должно быть
предположения, что все сделки — золото.

Предполагаемые поведенческие причины потерь (проверяются по данным, а не
принимаются как данность): прибыльная сделка закрывается в убыток; после
выигрыша растёт объём; вход рядом с новостями; стоп не выставлен заранее или
отодвигается; после убытка хочется отыграться. **Не закладывать заранее вывод,
что анализ рынка верен, что новости обязательно убыточны или что соблюдение
правил гарантирует прибыль.**

Бот проверяет введённый план и ведёт журнал. Он **не ставит стоп у брокера и не
может запретить реальный вход**. Формулировки в интерфейсе — точные: «План
проверен», «Факт входа записан», «Пользователь подтвердил установку стопа».

## 5. Рынки и инструменты

Во всех формах сделки, фильтрах и настройке счёта — связка **«Рынок →
Инструмент»**. Первый список сужает второй. Второй — комбобокс с поиском,
группами, избранным и недавно использованными.

| Рынок | Стартовый справочник | Особенность |
|---|---|---|
| Forex | EUR/USD, GBP/USD, USD/JPY, USD/CHF, AUD/USD, USD/CAD | Базовая/котируемая валюта, размер лота, определение пункта |
| Металлы | XAU/USD, XAG/USD | Контракт и объёмная сетка конкретного брокера |
| Криптовалюты | BTC/USD, ETH/USD, BTC/USDT, ETH/USDT, SOL/USDT | Spot и линейные контракты различаются; funding — отдельной проводкой |
| Акции и ETF | AAPL, MSFT, TSLA, NVDA, SPY, QQQ | Штуки или разрешённые дробные доли, биржа, валюта котировки |
| Индексы | S&P 500, Nasdaq 100, DAX | Торговый продукт у брокера: CFD или иной явно заданный контракт |
| Энергоносители и сырьё | WTI, Brent, природный газ, медь | Вид продукта, единицы котировки, множитель, при необходимости срок |
| Другой рынок | Свой инструмент | Добавление с обязательной проверкой спецификации и модели расчёта |

Это справочник для поиска, а не заявление о доступности инструментов у брокера
владельца. **Непроверенные размеры контрактов вымышленными значениями не
заполнять** — показывать «Нужно настроить спецификацию».

У инструмента обязательны: стабильный id, рынок, тип продукта (`spot`,
`equity`, `cfd`, `linear_future` / `linear_perpetual` при реализованной
поддержке), отображаемое имя, код, брокерский символ, площадка при
необходимости, базовый актив, валюта котировки, единица объёма, расчётная
модель, статус настройки. Брокерский символ и алиасы не заменяют уникальную
идентичность инструмента.

`US500`, `NAS100`, `US100` зависят от брокера — универсальными тикерами их не
считать. Индекс сам по себе не является исполняемой позицией: для расчёта
выбирается конкретный продукт.

Поведение списка: на desktop комбобокс, на телефоне панель выбора с поиском;
поиск по коду, названию и алиасам («золото», `gold`, `XAUUSD`); избранное
сверху; последний инструмент запоминается в пределах счёта; после выбора
подставляется **версия спецификации этого инструмента на этом счёте**; поле
объёма подписывается «Лоты», «Штуки», «Монеты» или «Контракты»; смена рынка
очищает несовместимый инструмент; смена инструмента заново валидирует все
ценовые и объёмные поля; при неоднозначном символе бот и сайт требуют уточнить
продукт; в журнале и аналитике доступны фильтры «Все рынки» / «Все инструменты».

| `/trading/accounts` | Счета и настройки | Ведёт движения денег, спецификации, подключает бота |

Экономический календарь — внутри дневника и контекстных проверок, отдельного
экрана не заводить.

Пункт добавляется в `src/components/nav.ts` без `primary`. Команды перехода —
в `src/components/command-menu.tsx`.

**Первый запуск:** создать счёт (название, брокер, валюта, начальный баланс,
дата начала учёта, IANA-зона) → выбрать рынки и инструменты, проверив тип
продукта, валюты, единицу объёма, множитель, минимальный объём, шаг объёма,
минимальный объём закрытия и шаг цены → задать правила и режим предупреждений →
подключить Telegram по одноразовой ссылке → записать первую сделку либо открыть
демосчёт.

Если настройки не заполнены — показывать конкретное следующее действие.
Не изображать подключение к брокеру или проверку календаря, которых нет.

Спокойный профессиональный торговый кабинет: графитовые поверхности, чистая

## 8. Сценарии сделки

### 8.1. Проверка перед входом

Раздели **план сделки** и **факт исполнения**.

План: счёт, рынок, инструмент, направление, предполагаемые вход и стоп, объём
в его единицах, необязательная цель, сетап, эмоциональное состояние, план
выхода. До подтверждения рассчитываются:

- риск до исходного стопа в валюте счёта и процентах; при конвертации — также
  исходная сумма и курс;
- допустимый по личному лимиту объём с учётом спецификации;
- плановое R/R, если цель указана;
- P/L при движении на одну единицу цены и на тик; для Forex — на пункт, если
  его определение задано;
- уже открытый плановый риск и риск после добавления позиции;
- нарушения лимитов, период охлаждения, проверка новостного окна.

Действия плана: «Изменить», «Отложить», «Отменить», «Записать факт входа».
Последнее требует фактической цены, времени и подтверждения объёма; при
расхождении параметров проверка повторяется. **Просмотр расчёта сам по себе не
создаёт открытую сделку.**

Без стопа план не получает статус готового к входу. Стоп для нового long ниже
входа, для short выше. Стоп, равный входу, не задаёт ненулевой исходный риск.

Если минимальный доступный объём превышает лимит: «При заданном стопе и
минимальном объёме сделка не укладывается в ваш лимит». **Объём вверх не
округлять**, увеличить депозит или сузить стоп не предлагать.

### 8.2. Запись уже совершённой сделки

Отдельный режим «Уже вошёл / добавить из истории»: позволяет записать
фактический вход без стопа, после превышения лимита или во время паузы.
Нарушение и источник данных фиксируются, полная история сохраняется.

Ретроспективно заполненный чеклист **не выдавать за проверку до входа**.
Отдельно хранятся: время создания записи, время сделки, режим ввода, время
подтверждения проверки.

При неизвестном исходном стопе или балансе значения не выдумывать: `NULL`,
причина, состояние неполноты. P/L может быть известен, когда R и риск в
процентах — ещё нет.

### 8.3. Ведение открытой позиции

Карточка показывает рынок и инструмент, фактический вход, исходный и текущий
стопы, цель, исходный объём с единицей, остаток, реализованный P/L в валюте
счёта и доступные действия: «Частично закрыть», «Закрыть остаток», «Изменить
стоп», «Добавить заметку / скриншот».

**Исходный стоп и начальный риск сохраняются.** Перенос стопа к входу не
превращает исходный риск в ноль и не меняет исторические R.

Плавающий P/L без цены рынка не обещать. При ручной цене показывать время и
источник оценки. Без актуальной цены — «Плавающий результат не рассчитан».
Расчётный остаточный риск до стопов не является гарантией максимального убытка
и не является расчётом маржи.

Частичное закрытие доступно только при допустимых объёме выхода и остатке.
Для позиции 0.01 при минимальном закрытии и остатке 0.01 деление на 0.005 +
0.005 недоступно — показать причину; **невозможную частичную фиксацию
нарушением не считать**.

Не утверждать, что стоп на цене входа обеспечивает безубыток с учётом
комиссий, свопа и исполнения. Напоминание о переносе стопа показывать только
если это соответствует выбранному плану.

### 8.4. Закрытие и разбор

Сначала надёжно сохранить выход. Затем предложить короткий разбор: причина
выхода, эмоция после сделки, MFE/MAE (если известны), соблюдён ли план выхода,
один урок, необязательный скриншот.

Для MFE/MAE есть «Не знаю» и «Заполню позже». Их отсутствие не блокирует
закрытие и **не превращается в нулевую экскурсию**.

Карточка закрытой сделки содержит хронологию: план → вход → изменения стопа →
частичные выходы → закрытие → разбор. Рядом — P/L, R, соблюдение правил,
полнота данных, расходы и выходы с объёмами. Сравнение плана с фактом — одной
компактной таблицей. Для сделки без рыночных свечей — честная схема уровней и
событий, **вымышленный график рынка не рисовать**.

## 9. Математическое ядро

### Где оно живёт

**`src/domain/trading/`** — чистый TypeScript, без React и без обращений к базе,
покрытый vitest. Вызывается **только с сервера**: из Server Actions и из
обработчика Telegram. Фронтенд формул не содержит и не дублирует — он
форматирует готовые значения.

Причина отхода от «расчёты в SQL-функциях»: Docker в системе отсутствует,
локальный Postgres и pgTAP недоступны, поэтому 33 числовых теста в plpgsql
невозможно было бы прогонять в обычном `npm test`. Требование «одно
математическое ядро, а не две реализации» при этом соблюдено полностью.

**Роль SQL:** views и RPC агрегируют **уже сохранённые** значения — суммы,
счётчики, средние по сохранённым полям. Формулы риска, R и P/L в SQL не
повторяются. Generated columns — только для выражений, допустимых PostgreSQL;
агрегаты по выходам — во views.

### Точность

Деньги, цены и объёмы в базе — `numeric`. Наружу из views и RPC денежные поля
отдаются как **`::text`**: `supabase-js` превратил бы `numeric` в JS `number`
(float) и потерял точность. На сервере арифметика ведётся в целых наименьших
единицах либо через строковую десятичную арифметику; **JavaScript float не
является источником финансовых итогов**. Округление для показа не меняет
хранимые суммы.

Моменты событий — `timestamptz`. Дата дневника — локальная `date`, вычисленная
по сохранённой IANA-зоне счёта через `at time zone`. Постоянный сдвиг UTC в коде
для торговли не использовать (в личных финансах он оставлен намеренно, см. 2.4).

### Формулы линейной модели

Обозначения: `d = +1` для long и `−1` для short; `q0` — начальный объём в
единицах спецификации; `C` — сохранённый множитель, переводящий «изменение цены
× объём» в сумму в валюте расчёта инструмента; `E` — фактический вход;
`S0` — исходный стоп; `T` — цель. Для простого spot/акций при объёме в штуках
или монетах `C = 1`; для лотов и контрактов берётся подтверждённый множитель
конкретного продукта.

Для базовой линейной модели валюта расчёта совпадает с валютой котировки.
Контракт с другим способом расчёта в эту модель автоматически не включать.

```text
initial_distance      = abs(E − S0)
initial_risk_quote    = initial_distance × q0 × C
initial_risk_account  = initial_risk_quote × fx_quote_to_account_at_entry
risk_pct              = 100 × initial_risk_account / balance_at_entry
planned_rr            = d × (T − E) / initial_distance

exit_gross_quote_i    = d × (exit_price_i − E) × exit_quantity_i × C
exit_gross_account_i  = exit_gross_quote_i × fx_quote_to_account_at_exit_i
gross_realized_account = Σ exit_gross_account_i
remaining_quantity    = q0 − Σ exit_quantity_i
avg_exit_price        = Σ(exit_price_i × exit_quantity_i) / Σ exit_quantity_i

net_realized_account  = gross_realized_account + Σ signed_adjustments_in_account_currency
final_R               = net_realized_account / initial_risk_account   [для закрытой сделки]

price_mfe_R           = max(0, d × (mfe_price − E)) / initial_distance
price_mae_R           = max(0, −d × (mae_price − E)) / initial_distance
```

Расходы — однозначно: комиссия списывается отрицательной суммой, своп может
быть отрицательным или положительным. Отрицательное списание не вычитать
повторно. Все изменения денег учитываются по времени фактической проводки.
Баланс меняется при частичном выходе и списании комиссии, а не только при
финальном закрытии.

`final_R` для неизвестного риска — **`NULL`, а не ноль**. До полного закрытия
можно показывать `realized_R_so_far`, явно отличая его от итогового результата.
`planned_rr` неизвестен без цели; цель с неправильной стороны входа **не
превращать в положительное R/R через `abs`**.

### Допустимый объём

Найти максимальный **допустимый спецификацией** объём, не превышающий
`risk_budget_account / (initial_distance × C × fx_quote_to_account)`. Учитывать
минимальный объём, шаг, максимум и модель сетки объёмов брокера. Округление —
только вниз к допустимому значению. При отсутствии допустимого объёма результат
«не помещается в лимит». **При неизвестном курсе расчёт нельзя одобрить как
проверенный.**

Плановый риск до стопа и оценка расходов показываются раздельно. Гэпы,
проскальзывание и неизвестные расходы могут увеличить фактический убыток.

Цент-счёт одним изменением `min_lot` не моделировать: нужны денежные единицы,
спецификация и правила конвертации. В первой версии такую конфигурацию явно
запретить до отдельной реализации.

### Валюты и рынки

- Курс хранится как «единиц валюты счёта за одну единицу валюты исходной
  суммы», со временем, источником и признаком оценки.
- Риск при входе использует снимок курса на входе. P/L выхода и каждая
  комиссия/своп/funding конвертируются по соответствующим событиям. **История
  не пересчитывается по сегодняшнему курсу.**
- Без подключённого источника разрешён подтверждённый ручной курс. Его
  отсутствие оставляет денежную метрику неизвестной, а не нулевой.
- **USD и USDT — разные валюты.** Курс 1:1 без явно записанного предположения
  пользователя не подставлять.
- Для счетов в разных валютах — либо раздельные итоги, либо явная валюта отчёта
  с воспроизводимой конвертацией. Разноимённые суммы не складывать.
- Для акций и spot различать **денежное финансирование покупки** и **расчётный
  торговый результат**. В первой версии вести капитал журнала, реализованный
  P/L и внешние потоки, не выдавая их за доступный cash balance брокера.
- Плечо, обеспечение, доступность short и торговое расписание зависят от
  продукта. Без этих параметров нельзя подтверждать исполнимость сделки,
  рассчитывать ликвидацию или свободную маржу; фактическую сделку записать
  можно — с пометкой неполных данных.
- Корпоративные действия, экспирация и ролловер «сами» не происходят. Если
  поддержки нет — указать ограничение и предложить ручные документированные
  корректировки, не меняя исходную историю незаметно.

### Баланс и движение денег

Начальный баланс фиксируется на определённую дату ровно один раз. Последующее
пополнение **не является прибылью**.

```text
book_balance(t) = opening_balance
                + Σ deposits − Σ withdrawals
                + Σ realized_trade_postings
                + Σ explicit_nontrade_adjustments

cumulative_trading_pnl(t) = Σ realized_trade_postings
```

Проводки торгового результата включают валовой P/L выходов и подписанные
расходы. Производная проводка уникальна для исходного события; повторная
обработка не меняет деньги второй раз. Ручная сверка с брокером — отдельная
операция с причиной, внутри P/L её не прятать.

В интерфейсе: «Учётный баланс журнала» и дата последней сверки. Название
«Капитал / equity» использовать только при наличии корректной оценки всех
открытых позиций и валют.

### Просадка

Основная просадка первой версии — **денежная**: падение накопленного
реализованного торгового результата от его исторического максимума. Пополнение
или вывод не становятся торговой прибылью или убытком.

Процентную просадку по пополняемому балансу не вычислять и на кривую P/L,
начинающуюся с нуля, не делить. Процентная доходность добавляется только
с явно описанным индексом доходности, нейтрализующим внешние потоки, с
проверками и обработкой нулевой/отрицательной базы. Иначе — денежная просадка
и объяснение ограничения.

### MFE/MAE и «отданная прибыль»

Различать:

1. **Ценовая экскурсия** — куда доходила цена; может быть введена вручную.
2. **Максимум стоимости позиции** — максимум суммы реализованного и плавающего
   результата с учётом объёма во времени; требует истории цен, выходов и
   расходов.

Для сделки с частичными выходами **нельзя** выдавать `price_mfe_R − final_R` за
точную упущенную прибыль: часть объёма могла быть закрыта до экстремума.
При наличии только экстремальных цен показывать «Ценовая возможность / итог
сделки» с явной пометкой об ориентировочности. Точный `position_giveback_R`
считать только при достаточной временной истории. Любой такой разрыв **не
называть доказанным убытком из-за поведения**.

Проверять согласованность экстремумов с направлением, входом и известными
ценами исполнений. Хранить источник (`manual`, `imported`, `market_data`) и
признак оценки. Пропуски остаются пропусками.

### Снимок сделки

В момент входа сохранить: инструмент, единицы, версию спецификации, набор
правил, часовой пояс счёта, план выхода, курс конвертации, исходный стоп и
баланс непосредственно перед входом — с источником и признаком достоверности
баланса. Известный баланс должен учитывать все предшествующие движения, включая
частичные выходы других сделок.

Изменение настроек применяется к будущим входам. Исторические параметры
автоматически не переписываются: **смена минимального лота сама по себе не
меняет P/L старых сделок.**

Исправление фактической ошибки — отдельным действием с причиной и журналом
изменений. При вводе запоздавшей проводки обнаруживать затронутые снимки
баланса: помечать их для сверки и предлагать явный версионированный перерасчёт,
сохраняя прежнюю оценку.

### Целостность и конкурентность

- Выход не может предшествовать входу; объёмы положительны и соответствуют
  спецификации.
- Суммарно закрытый объём не превышает начальный; финальное закрытие — при
  нулевом остатке.
- Проверка остатка и запись выхода — в одной транзакции с блокировкой
  родительской сделки (`select ... for update`) или эквивалентной защитой.
- Создание входа, снимка баланса и движения денег сериализуются на уровне счёта
  там, где это нужно для согласованности.
- Для одинаковых времён — явная стабильная последовательность событий.
- Два параллельных запроса не могут закрыть один остаток дважды.
- `cancelled` относится к плану без исполнения. Ошибочную фактическую запись
  аннулировать понятным действием с аудитом и согласованным пересчётом.
- Архивирование счёта или сетапа сохраняет историю. Каскадное удаление обычной
  кнопкой управления счётом не предлагать.

## 11. Дисциплина без самообмана

### Три раздельные группы

**Проверка до входа:** исходный стоп, плановый риск, число входов за день,
наличие сетапа, проверка новостей, активная пауза, самооценка состояния.

**Соблюдение плана в ходе сделки:** отодвигание стопа, выходы относительно
заранее записанных условий, превышение заявленных ограничений.

**Результаты и диагностические признаки:** прибыль/убыток, размер MFE, возврат
из плюса в минус, изменение объёма после победы или проигрыша.

**Результат сделки не смешивать с оценкой дисциплины.** «Была +1R, закрылась в
минус» — наблюдение о результате, а не доказательство нарушения. Иначе график
«дисциплина ↔ прибыль» будет частично отражать собственную формулу оценки.

### Настраиваемые правила

Лимит риска на сделку; лимит суммарного открытого планового риска; дневной
лимит реализованного убытка относительно сохранённого баланса начала дня;
максимум входов за день; пауза после убытка; пауза после серии убытков; окно
до/после важных событий; обязательность сетапа и чеклиста; запрет отодвигать
стоп дальше от входа; правила фиксации — только если указаны в плане и
технически выполнимы.

Пороги задаёт пользователь. **Не задавать 5–8 % как универсальную «безопасную
зону».** Значение 6 % в тестах раздела 16 — тестовый параметр, не рекомендация.

У правила: стабильный код, версия, область применения, важность, вес, режим
`warn` / `block_plan`, текст и параметры. Новый алгоритм проверки требует
реализации и теста, а не только строки в таблице.

### Оценка и полнота

Статусы проверки: `passed`, `failed`, `unknown`, `not_applicable`. **Неизвестное
не считается выполненным.**

```text
discipline_score = 100 × Σ weights(passed) / Σ weights(passed + failed)
coverage         = 100 × Σ weights(passed + failed) / Σ weights(passed + failed + unknown)
```

При пустом знаменателе — «Недостаточно данных». Рядом со score показывать
coverage, число проверок и источник. Для сравнения с результатом использовать
оценку, зафиксированную **до входа**; поздно заполненные проверки помечать и
позволять исключить. Сделки с неизвестным R не скрывать — показывать их число
отдельно.

### Последовательности

«Предыдущая закрытая сделка» для паузы — сделка того же счёта, **закрытая до**
рассматриваемого входа. Результат позиции, которая тогда оставалась открытой,
использовать нельзя.

Объёмы сравнивать только для сопоставимых инструментов и спецификаций. 0.01
лота золота, 10 акций и 0.1 BTC — не один числовой показатель. Между разными
инструментами сравнивать риск в валюте счёта и процентах. Больший объём при
более коротком стопе сам по себе не доказывает повышенный риск. «Возможный
отыгрыш» — гипотеза; нарушение паузы определяется установленным правилом.

Лимит «не больше трёх входов» нарушается начиная с четвёртого, а не у всех
сделок дня. Границы дня — по сохранённой зоне счёта. Выходные и дни без
торговли не считать пропусками дневника без соответствующей настройки.

## 13. Аналитика

### Единые определения

- **P/L периода:** реализованные проводки, произошедшие в периоде, включая
  частичные выходы и расходы.
- **Статистика завершённых сделок:** сделки, закрытые в периоде, с полным
  итогом каждой.
- Эти выборки дают разные суммы. Подписывать основание периода и объяснять
  различие в tooltip.
- Win rate: прибыльные / все закрытые; безубыточные показывать отдельно,
  определив точность сравнения.
- Profit factor: сумма положительных итогов / модуль суммы отрицательных. При
  отсутствии потерь объяснять состоянием, не рисовать `0` или ложное число.
- Средний R и сумма R — только по известным валидным R, с размером выборки.
- Сумма R — не процентная доходность счёта.
- Сравнение периодов — одинаковой длительности, с явной отметкой неполного
  текущего периода. При нулевой базе процент изменения не выдумывать.

### Разделы

1. **Результат:** P/L, баланс, поток денег, накопленный R, распределение R,
   денежная просадка, длительность, расходы.
2. **Дисциплина:** оценка до входа против итогового R, частота проверяемых
   нарушений, полнота журналирования.
3. **Исполнение плана:** исходный риск, переносы стопа, выходы, ценовая
   экскурсия и ограничения её интерпретации.
4. **Контекст:** рынки, инструменты, сетапы, эмоции, направление, час и день
   недели, длительность, наличие новостей.

Сравнение рынков и инструментов: число сделок, чистый результат в валюте
выбранного счёта, средний R, дисциплина, полнота данных. **Сырые лоты разных
рынков не суммировать и не сравнивать как однородный объём.** Рынок и инструмент
включать в подписи точек, экспорт и детальную фильтрацию.

В каждой группе показывать число сделок, период, средний/медианный R при
наличии, win rate и покрытие данных. Редкие группы помечать как малую выборку;
статистическую достоверность одним произвольным порогом числа сделок не
изображать.

Для новостей различать «вошёл в окне события» и «держал позицию в окне
события». Применимость событий и правил к валютам, рынкам и инструментам
настраивается. Макрособытие США не объявлять механически одинаковым запретом
для всех инструментов; корпоративное событие привязывать к соответствующей
акции. **Отсутствие записи в неполном календаре — не доказательство отсутствия
новостей.** Показывать источник, дату обновления и статус проверки; неизвестный
статус не превращается в «вне новостей».

### Панель наблюдений

Карточки на реальных агрегатах: «Плановый риск выше личного лимита: N сделок»;
«Объём вырос после прибыльной сделки: N случаев»; «Записан вход до окончания
паузы: N случаев»; «Данные о стопе отсутствуют в N сделках»; «Для сетапа A пока
мало наблюдений».

У каждого наблюдения — период, основание, число сделок и действие «Показать
сделки». Данные не подгонять под ожидаемый вывод.

**Суммарный P/L сделок с нарушением не называть «стоимостью нарушения»:**
причинная связь не установлена. Одна сделка может нарушать несколько правил,
поэтому суммы групп пересекаются и не складываются в независимые потери.

### Недельный обзор

Структура: что произошло со счётом → как соблюдались правила → какие данные
неполны → одно наблюдение на следующую неделю → заметка пользователя.

Обзор формируется **детерминированно по метрикам**. В проекте есть AI-ассистент
с цепочкой провайдеров (`src/lib/assistant/`), но основные выводы, расчёты и
разбор обязаны работать без него. Подключение LLM к обзору — отдельное будущее
расширение по согласованию.

Поощрять заполненный разбор и соблюдение процесса. Конфетти за прибыль, награды
за число сделок и механики, подталкивающие торговать чаще, не добавлять.

## 14. Дневник, стратегии, экспорт

**Дневник:** календарь месяца с результатом и отдельным индикатором
завершённости разбора. Различать день без торговли, запланированный выходной,
открытые позиции и пропущенный итог. Переход в день показывает план, настроение,
события, сделки и урок.

**Стратегия/сетап:** название, признаки допустимого входа, условия отмены идеи,
правило стопа, план выхода, примеры, чеклист. Изменение сетапа создаёт новую
версию; сделки сохраняют использованные условия.

**Поиск и фильтры:** счёт, даты, рынок, инструмент, тип продукта, направление,
статус, сетап, эмоция, правило, результат, полнота, источник ввода. Поиск по
заметкам, сортировка и **серверная** пагинация.

**Экспорт:** CSV сделок с выходами и основными метриками, журнал движения денег,
JSON резервной выгрузки с версией схемы. CSV корректно обрабатывает кириллицу,
разделители, переносы строк и потенциальные формулы в пользовательском тексте.
Экспорт следует тем же правилам доступа, что и UI.

Импорт брокерских отчётов — отдельное развитие. Работающим не заявлять, пока
нет формата, сопоставления полей, сверки и защиты от дублей.

## 15. Защита данных и производительность

Авторизация — существующая. Личные записи изолировать по владельцу, включая
дочерние сущности, вложения, views, RPC и экспорт. **Проверять, что счёт и
сделка принадлежат одному владельцу** — составными ключами (решение 7 раздела 3).

Для доступных клиенту таблиц — grants и RLS с проверкой чтения и записи,
включая `with check`. Views создавать с `security_invoker = true` (PostgreSQL
17.6 поддерживает). `security definer` для обхода ошибок доступа не добавлять.

Внутренние таблицы доставки и привязки получают отдельную модель доступа.
Service-role ключ остаётся на сервере.

Скриншоты — в **приватном** бакете Supabase Storage (в проекте Storage пока не
используется, бакет и политики создаются этим модулем). Хранить путь объекта,
а не вечный публичный URL; выдавать временный доступ после проверки владельца.
Проверять тип и размер файла.

Агрегаты и фильтрацию выполнять на сервере и в базе. Всю историю в браузер ради
KPI не загружать. Индексы проектировать по запросам: владелец/счёт/дата, выходы
по сделке, проводки по счёту и времени, новости по времени, pending-задачи по
состоянию и сроку.

Кэш разграничивать по пользователю, счёту и фильтрам. **Общий кэш приватной
аналитики для разных пользователей недопустим.** `cacheComponents` в проекте
выключен — приватные страницы динамические по умолчанию, чего и нужно.

доступа или инструментов — явно перечислить непроверенные сценарии.

## 17. Порядок работ

Фаза аудита выполнена, её результаты — разделы 2 и 3. Начинать с этапа 1 после
«го» владельца.

| Этап | Содержание | Признак готовности |
|---|---|---|
| 1 | Математическое ядро `src/domain/trading/**` + миграции схемы, RLS, индексы, составные ключи владельца | 33 теста раздела 16 проходят в `npm test`; `npx supabase db push` применяется без ошибок |
| 2 | Сквозной сценарий на сайте: счёт → инструмент и спецификация → план → факт входа → выходы → карточка сделки → журнал | Сделка проходит путь целиком через интерфейс |
| 3 | Telegram: хеш токена, inbox, outbox, восстановление обработки, торговые команды, напоминания | Тесты 15, 16, 23, 36, 38 проходят; ввод расходов не сломан |
| 4 | Обзор, аналитика, дневник, наблюдения | Клик по показателю открывает сделки, из которых он посчитан |
| 5 | Визуальная полировка, экспорт, сквозная проверка, документация | Тест 39; README и `.env.example` обновлены |

После каждого этапа — короткий отчёт и продолжение по плану. Повторно
спрашивать только при существенном изменении объёма, платном подключении,
разрушительной миграции или необходимости невыданного доступа. Публикацию,
изменение production и отправку сообщений реальным пользователям выполнять
только отдельно согласованным действием.

### Что должно остаться в проекте

- рабочие экраны и серверные операции;
- миграции, индексы, ограничения, RLS и безопасные views;
- бот с инструкцией настройки вебхука;
- обновлённый `.env.example` без реальных секретов;
- тесты критических расчётов, конкурентных операций и доступа;
- явно отделённый демосчёт;
- раздел в `README.md`: запуск, настройка счёта, бот, cron/воркер, формулы,
  ограничения, диагностика;
- инструкция применения миграций и безопасного отката модуля.

В финальном отчёте перечислить реализованное, выполненные проверки, известные
ограничения и необходимые ручные настройки. Отдельно указать, **что
действительно проверено, а что требует окружения владельца**. Непроверенное
за готовое не выдавать.

### Критерий завершения

Модуль готов, когда реальная записанная сделка проходит путь от ввода до
корректной аналитики, повтор запроса не меняет деньги дважды, другой
пользователь не получает доступ к данным, а интерфейс удобно работает с
телефона. Красивого демо без этого недостаточно.

## 18. Правила репозитория

Соблюдать наравне с продуктовыми требованиями.

1. **`AGENTS.md`**: это не тот Next.js, что в обучающих данных. Перед написанием
   кода, затрагивающего API фреймворка, читать соответствующий раздел в
   `node_modules/next/dist/docs/`. Блок в `AGENTS.md` дописывается самим
   `next dev` — удалять его из диффа бессмысленно.
2. **Язык:** интерфейс, комментарии, сообщения об ошибках и коммиты — русские.
3. **Комментарии объясняют «почему», а не «что».** Образцы стиля —
   `src/domain/finance/day.ts`, `src/lib/demo/store.tsx`. Комментарий,
   пересказывающий код, не нужен.
4. **Не придумывать данные.** Суммы, курсы, спецификации, даты и котировки не
   заполнять правдоподобными значениями. Неизвестное остаётся `NULL` с причиной.
5. **Тесты:** vitest, окружение `node` по умолчанию, компонентные помечаются
   `// @vitest-environment jsdom`. Существующие 250 тестов должны продолжать
   проходить.
6. **Перед коммитом:** `npm run typecheck`, `npm run lint`, `npm test`,
   `npm run build` — все зелёные.
7. **Коммиты** небольшие и осмысленные, с объяснением причины изменения в теле.
   Чужие незавершённые изменения и секреты в коммит не попадают.
8. **Не выводить содержимое `.env.local`.**
9. **Существующие миграции не редактировать** — только новые файлы.
10. **Не ломать существующие маршруты и функции**: личные финансы, задачи,
    планы, календарь, ассистент, авторизация, `DemoStoreProvider`.
